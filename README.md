# dev-clean

Автоочищення dev-сміття на Linux: збіркові кеші, які самі відновлюються, але з'їдають сотні гігабайтів.

Щотижнева чистка через systemd user timer плюс аварійний тригер, який спрацьовує, коли диск майже заповнений.

**Принцип:** видаляється лише те, що (а) відновлюється автоматично і (б) давно не використовувалось. Ціна помилки — одна довга перезбірка, а не втрачені дані. Контейнери Docker, volumes та вихідний код не чіпаються ніколи.

## Що чистить

| Ціль | Правило |
|---|---|
| Docker build cache, dangling-образи | старші за 2 тижні |
| Rust `target/` | 14+ днів без змін у репозиторії; лише справжній target cargo (з `CACHEDIR.TAG`) |
| Rust `target/debug` в **активних** репо | target ≥ 20 ГБ і не збирався 7+ днів |
| `node_modules` | проєкт без змін 60+ днів |
| `.next`, `.turbo`, `dist`, `build`, `.venv`, `__pycache__`, `coverage` | проєкт без змін 60+ днів і лише якщо `git check-ignore` підтверджує, що це сміття |
| `.turbo/cache` | записи, старші 30 днів, **плюс** LRU-обрізання до 8 ГБ на репозиторій |
| `.next/dev` (кеш turbopack dev-сервера) | 14+ днів без змін |
| pnpm store, npm `_cacache`, `uv cache`, `.crate` | prune / TTL 90 днів |
| `~/.cache` | тека застосунку, у якій 60+ днів нічого не читали й не змінювали, — цілком |
| Кошик | покладене 30+ днів тому |
| Кошик синку скілів Claude Code (`~/.claude/skills/.trash`) | покладене 30+ днів тому |
| Flatpak | рантайми без посилань |

Кілька правил варто пояснити окремо:

- **Ліміт розміру `.turbo/cache`.** Один запис кешу turborepo може важити кілька гігабайтів, тож тека доростає до 80+ ГБ за тиждень — і правило «старші 30 днів» не спрацьовує жодного разу. Тому діє ще й ліміт розміру: найстаріші записи видаляються, доки тека не влізе в `TURBO_CACHE_LIMIT_MB`.
- **`target/debug` в активних репо.** Правило «14 днів без змін» ніколи не спрацює на репозиторії, з яким працюєш щодня, — а саме там target і доростає до 90+ ГБ.
- **Що таке «проєкт».** Найближча тека вгору з lockfile (`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`, `bun.lock`, `deno.lock`), тобто в монорепо — увесь workspace. Інакше в активному монорепо зникали б `node_modules` і `dist` пакета, який просто давно не редагували.
- **`~/.cache` — лише цілими теками.** Там живуть і тулчейни (ms-playwright, corepack, node-gyp, prisma), які перевіряють тільки наявність теки версії. Якщо видаляти окремі старі файли, тулчейн лишиться напівживим і сам себе не перекачає, а відсутню теку кожен із них відновлює сам.

## Встановлення

```sh
git clone https://github.com/<user>/dev-clean.git ~/Documents/dev-clean
~/Documents/dev-clean/install.sh
```

`install.sh` створює симлінки в `~/.local/bin`, копіює systemd-юніти в `~/.config/systemd/user` і вмикає таймери. Скрипти лишаються в репозиторії — `git pull` одразу оновлює те, що виконується.

### Системні кеші

Скрипт працює від користувача і root не отримує: інакше знадобилося б NOPASSWD-правило в sudoers. Системні кеші натомість обмежують штатні налаштування, і вони діють постійно, а не раз на тиждень.

**apt.** `apt-get` тримає кожен завантажений `.deb` назавжди, тож `/var/cache/apt/archives` росте без меж. Конфіг ставиться один раз:

```sh
sudo install -m 644 ~/Documents/dev-clean/apt/99dev-clean /etc/apt/apt.conf.d/
```

Він вмикає видалення `.deb` одразу після встановлення і щотижневий `apt-get autoclean` через `apt-daily-upgrade.timer`. На відміну від `clean`, `autoclean` не чіпає завантажені наперед, але ще не встановлені оновлення. Ставиться копією, а не симлінком, бо apt читає цей файл від root. `install.sh` нагадає, якщо конфіг не встановлено або він застарів.

**journald.** Журнал обмежує сам journald через `SystemMaxUse` (на Pop!_OS — 1000M). Потрібна менша стеля — задай `SystemMaxUse=` у `/etc/systemd/journald.conf.d/`.

## Розклад

| Юніт | Коли | Що робить |
|---|---|---|
| `dev-clean.timer` | щонеділі 12:00 (±30 хв, `Persistent=true`) | повна чистка |
| `dev-clean-watch.timer` | щогодини | одна команда `df` |

Watch запускає чистку тільки якщо диск заповнений на `DEV_CLEAN_THRESHOLD`% і остання чистка була давніше ніж `DEV_CLEAN_COOLDOWN_H` годин тому. Інакше — мовчки виходить, не пишучи в лог. Якщо чистка вже відпрацювала, а місця все одно бракує, надсилає критичне сповіщення замість повторного холостого запуску.

`Persistent=true` означає, що пропущений через вимкнений комп'ютер запуск відбудеться при найближчому вмиканні.

## Логи

```sh
tail -f ~/.local/state/dev-clean.log
```

Пишемо у файл, а не лише в journald: для user-юнітів journald часто не персистентний, і `journalctl --user -u dev-clean.service` показує «No entries» навіть після реального запуску. Лог ротується — при перевищенні 1 МБ лишаються останні 2000 рядків.

## Ручний запуск

```sh
systemctl --user start dev-clean.service   # звичайний запуск
dev-clean.sh                               # те саме, з виводом у термінал
```

## Налаштування

Усі пороги перевизначаються змінними оточення — у `systemd/dev-clean.service` через `Environment=`, або разово перед ручним запуском.

| Змінна | Типове | Значення |
|---|---|---|
| `DEV_CLEAN_SCAN_ROOT` | `$HOME/Documents` | корені сканування, кілька — через пробіл |
| `DEV_CLEAN_SCAN_DEPTH` | `10` | глибина обходу |
| `TURBO_CACHE_LIMIT_MB` | `8192` | ліміт `.turbo/cache` на репозиторій |
| `NEXT_DEV_STALE_DAYS` | `14` | вік `.next/dev` для видалення |
| `RUST_TARGET_BIG_GB` | `20` | з якого розміру target вважається завеликим |
| `RUST_TARGET_BIG_STALE_DAYS` | `7` | простій, після якого чиститься його `debug/` |
| `SKILLS_TRASH_DAYS` | `30` | вік копій у кошику синку скілів Claude Code |
| `DEV_CLEAN_THRESHOLD` | `90` | % заповнення для аварійного тригера |
| `DEV_CLEAN_COOLDOWN_H` | `6` | мінімальний інтервал між аварійними запусками |
| `DEV_CLEAN_LOG` | `~/.local/state/dev-clean.log` | файл логу |

Глибина 10 не випадкова: git worktree в структурі `worktrees/<repo>/<branch>/<repo>/apps/<app>/.next/dev` лежить рівно на 8 рівнях, тож типового `maxdepth 4` не вистачає, а 8 — впритул.

## Особливості

**`noatime`.** Скрипт перевіряє через `findmnt`, чи змонтований диск з `noatime`. Якщо так, atime ненадійний: чистка `~/.cache` за часом доступу свідомо пропускається, а npm-кеш чиститься за mtime-TTL. На звичайному `relatime` працює atime-правило.

**PATH.** systemd дає мінімальний PATH, тому скрипт сам додає `$PNPM_HOME` і `~/.local/bin` — інакше `pnpm`/`uv` не знайдуться.

**Обхід дерева.** `find` не спускається в `node_modules`, `.git` і `target`: це і швидше, і не дає знайти збіркові теки всередині залежностей. Повний обхід ~250 ГБ дерева займає близько двох секунд.

**Себе не з'їсть.** Репозиторій може лежати всередині `DEV_CLEAN_SCAN_ROOT` — під правила потрапляють лише збіркові теки, яких тут немає.
